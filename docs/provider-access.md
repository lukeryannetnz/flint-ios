# Provider access and cancellation

`VaultFileServing` and bookmark resolution/creation return asynchronous results. Each call requires a `ProviderRequest` containing its vault root, priority and `ProviderAttempt`. A loading attempt shares one 30-second foreground budget across bookmark setup, security scope acquisition, discovery and initial content. Only a corruption error from bookmark resolution itself clears saved permission data; later discovery/read corruption preserves the resolved bookmark. Background/inactive time pauses that budget; stage changes do not reset it. Loading shows a slow indicator after five foreground seconds.

`ProviderExecutor` owns blocking work: two global slots, one job per standardized vault root, and at most 32 pending jobs. Unresolved bookmarks share a conservative root identity until resolved. Explicit actions precede optional jobs, with FIFO within priority. A separate decode lane has one slot. Queued cancellation removes the job; queue saturation returns a typed failure. A root with a draining worker rejects retries, and two draining workers reject new work immediately. Another root may use the remaining free slot.

Logical cancellation or timeout returns to the UI independently of provider completion. Each operation owns its coordinators and requests `NSFileCoordinator.cancel()`. Cancellation cannot guarantee that an accessor or scope acquisition actually stops. The worker retains its slot and source/destination scope leases until it returns. No replacement worker is spawned for a blocked accessor. If scope acquisition itself returns after cancellation, its lease is balanced and no subsequent source scope or accessor is started. Scope start and balanced stop run off the main thread; a separate lease retained by the current UI keeps the active vault accessible.

Actual mutation outcomes remain with their attempt after logical cancellation. Created URLs, complete image-import results and valueless saves have distinct typed outcomes. A create retry waits for the original result and opens an already-created item rather than creating a duplicate. Successful note creations also retain their URL across later discovery/read failures, so the same-name retry refreshes and opens that existing note. Save snapshots retain text, destination and revision, serialize writes, and keep newer revisions dirty. An uncertain save cannot overlap its retry. Navigation saves pending text first and stays at the original destination on failure. Creation releases its busy state before delegating navigation, including when that save fails; its created result remains retryable. Metadata refresh failure does not turn a completed write into a failed save.

Timed-out file/camera imports retain their attempt and operation; stale successful imports retain their complete result. Pending imports are kept by original note URL for this process. An in-flight request is registered before provider dispatch, preventing a second file/camera callback from creating another asset or clearing its busy state. Another import into that note waits for unresolved success/running outcomes; completed failures and requests that never started are removed before new admission, without requiring Recover. The original note exposes **Recover image at cursor**: it returns the completed asset/Markdown/alt text once without another copy or encode, or explains that the worker is still stopping. Returning to another note or vault cannot insert the late image there; returning to the original note exposes recovery again. Actual failure permits selecting a source again. No recovery action deletes managed assets. Pending-image reconciliation is process-local; restart recovery is not claimed by this phase.

Vault/document/navigation generations guard asynchronous state publication, including alerts and diagnostic export. Pending note selection is published separately from retained editor content and resets on failure/cancellation; selecting that row again immediately retries it. Programmatic browser selection only synchronizes presentation; it does not initiate another read. Loading and pending-note controls can cancel immediately. Recovery can retry, choose another vault, or share a sanitized app-local JSON-lines snapshot even while both provider workers drain. Sharing is bounded to one 20 MiB artifact and cleans up on dismissal, stale completion and next startup. Its manifest discloses missing/delayed reports, unknown correlation and truncation. Sharing never uploads automatically.

`ProviderExecutorTests` block both before and inside a coordinator accessor, advance a controlled foreground clock, and assert immediate logical timeout, coordinator cancellation, retained scopes/slots, actual completion, and exactly one logical terminal event plus a late-finish observation. Further tests cover both-worker saturation, queue bounds, priorities, task cancellation, shared foreground budgets and worker-thread execution through the real file adapter. An injected worker-completion observer runs after scope/slot release; fault cleanup assertions await this boundary rather than assuming cleanup completes within a short polling window. Hosted CI uses serial simulator test runners; provider concurrency is still exercised inside the process. Model fault tests cover stale results, dirty revisions, uncertain creation/save outcomes and recovery/export usability.

Phase 4 tasks 4.1–4.3 add metadata-only discovery, demand-driven previews and bounded editable reads. Discovery examines at most 256 entries and publishes at most 64 notes per job, releasing its worker between batches so explicit reads and saves precede optional continuation. Recent sorting remains modification date descending with path ties; folder sorting remains creation date descending. Selection happens once from the first usable sorted batch and later batches never override it. Incomplete discovery retains available notes and exposes Retry; only completed discovery can establish an empty vault. Missing regular-file metadata is an incomplete observation, not empty success.

Visible rows request previews at optional priority. Offscreen cancellation invalidates their request; cache entries use URL, observed modification date and source size, and invalidate on successful save or explicit discovery refresh. The shared cache/presentation values hold at most 4 MiB of excerpt bytes and 512 entries with least-recently-used eviction. A successful full listing after creation/save invalidates any older incremental cursor before publication, preventing later pruning of newly created notes. Sources read at most 64 KiB in 16 KiB chunks; a coordinated file-handle end-offset check distinguishes exact-limit EOF without reading another byte; split terminal UTF-8 sequences are omitted from truncated prefixes, while invalid content fails. Omitted, pending, unavailable, empty and truncated states are distinct. No preview is read by enumeration.

Selected notes read complete UTF-8 in bounded chunks with an 8 MiB source limit, independent of missing or stale metadata. At most one extra byte probes overflow; oversized, invalid and interrupted reads return no editable partial text. Pending-note presentation leaves the browser usable, and cancellation or a newer selection rejects old results. The initial selection shares setup’s foreground deadline; later discovery and explicit selections have their own bounded attempts. A valid bookmark is persisted once usable metadata is published, and restoration succeeds at the usable browser boundary even if selected content fails.

Save snapshot/order protections already exist, but explicit retain/discard choices and protected durable document recovery remain tasks 4.4–4.6. Inline/viewer image source reads, picker staging and image cache/downsampling remain phase 5. Rich diagnostic preview and clear-history controls remain phase 6. Simulator faults demonstrate scheduling and state guarantees; physical-iPhone Dropbox responsiveness, memory and provider behavior still require device validation.

Successful note creations retain their destination before stale navigation is rejected. Selecting another note in the same vault does not discard the result; retrying creation opens the existing note without another mutation.
